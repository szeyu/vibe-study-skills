# Multi-File Notes

## Improving existing folders

Inventory the current notes and assets before editing. Preserve the user's folder tree, filenames, reading order, and existing hubs. Improve the original Markdown files directly; do not add a parallel study guide or move answers into a separate new layer without a task-specific reason.

Assign each concept or derivation a primary home. Related notes may give a short contextual recap and a link, but should not repeat long derivations verbatim. Keep worked examples understandable without excessive navigation.

## Creating a new set

Start with the smallest structure that fits the material. Split when parts have distinct learning objectives or substantial reuse, not because a file passed an arbitrary line count. Keep a short definition in its parent note when a separate file would provide little value.

Follow the vault's naming conventions. Number files only if the vault uses numbers or a required reading sequence benefits from them. A flat collection of topic notes is often sufficient; concepts/techniques/examples/practice folders are optional, not a standard to impose.

Update an existing hub if one provides navigation. Create a new hub only when the set needs an entry point. Use unambiguous link paths and add previous/next navigation only where a sequence exists.

## Coverage

Track every in-scope note as unreviewed, reviewed unchanged, improved, or unresolved. Record the actual issue or reason for leaving it alone. Review dependencies and consistency across files as well as individual prose. Formatting-only changes do not count as substantive improvement.

At completion, state the scope covered and remaining gaps. If the task was a targeted pass, say so. Do not call the whole subject complete because several prominent notes were upgraded.
